# Drive Job status scenarios by data
Replace each scenario's hand-written `assertions` callback in `Job_status_spec.js` with data. Each scenario declares a `visible` object of booleans — `remainingAttempts`, `readyIn`, `lastError`, `retryButton` — and a single generic block (e.g. `itBehavesLikeVisibleSections(state, visible)` defined locally or in `support/`) generates the specs: "shows remaining attempts" / "does not show Remaining attempts", "shows Ready in" / "does not show Ready in", "shows Last error" / "does not show Last error", "shows a Retry button" / "does not show a Retry button". The generic block checks text via `state.container.textContent` (`'Remaining attempts'`, `'Ready in'`, `'Last error'`) and the button via `querySelectorAll('button')` looking for `textContent === 'Retry'`.

Checks that do not fit the generic shape stay as an optional `extraAssertions: (state) => { ... }` callback on the scenario: the "5s" countdown, "shows the job id", the collapsed `<details>` "Show error" check, the error message text (`connection refused` / `fatal timeout`), "shows Ready when readyInMs is 0", and the enqueued/failed "shows remaining attempts" value checks (`'3'` / `'2'`) if they cannot be expressed by the boolean alone. Make sure every existing `it` is still produced by either the generic loop or an `extraAssertions` callback — no assertion may be dropped. Scenario `job` fixtures and labels stay unchanged.
